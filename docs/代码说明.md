# 查重小助手：代码与维护说明

## 技术结构

纯静态网页，JavaScript ES Modules + 原生 DOM/CSS，不依赖服务端识别或账号系统。PaddleOCR v6 tiny 在 Web Worker 中通过 ONNX Runtime Web / WebAssembly 运行，照片仅在浏览器本机处理。IndexedDB 保存识别记录和图片，Cache Storage 保存静态资源与识别模型。

源码以小模块划分，解析和查重函数可以在 Node.js 中独立测试。识别数据不发送到 GitHub 或其他服务器。

## 识别流程

1. 导入时校验文件大小，计算照片字节的 SHA-256。本次批次内字节完全相同的照片共享一次识别结果，每条记录独立保存。
2. 模型初始化与图片解码并行。按图片方向解码，长边最多 3000 像素；不通过降低常规图片清晰度换取速度。
3. Worker 返回文字和坐标，按相近基线组合同行内容，保留标签与值的关系。微信电子凭证的合并单元格有独立的行归属处理。
4. 支付截图走各自专用规则；没有充分类型证据时走通用规则，不靠“微信号”等联系信息单独猜类型。
5. 金额、日期、单号等关键字段不完整时，先按缺失标签或文字内容区域补扫；必要时再作一次较宽范围扫描。正常完整凭证只运行一轮，最多三轮模型推理，避免无限重试。
6. 补扫只补缺失/无效字段，不覆盖已有有效值。单号的“可以录入”与“足以判重”分别判断，日期只有年月日也能保留识别到的流水号。
7. 校验后记录保存到本机。无法确定的字段保留明确提示，不将不确定的原价、优惠或其他数额冒充实付金额。

### 平台规则

- **支付宝**：首页优先商品说明；实付取顶部金额，付款时间与乘车时间分离。订单号与商家订单号分别保存。
- **微信**：区分商户支付、扫码付款、个人转账。个人转账使用转账时间，不用收款时间代替；截图保留可见收款人。电子转账凭证沿用隐藏收款方的既定界面规则。
- **退款**：微信截图保留原支付金额，退款金额和退款时间分开保存与导出，避免重复扣减。此工具的总金额不是退款抵扣后的净支出。
- **通用凭证**：按同一行或独立标签后内容提取金额、日期、商户、摘要、单号和机构。实付优先于合计；高优先级标签存在但为空/不可辨认时，不退而使用较低优先级金额。同级冲突自动重试，仍不明确则提示具体字段。
- **日期**：完整日期严格校验真实日历值。通用凭证允许只有日期或分钟，不补造秒数；Excel 保留文本精度，但排序使用实际日期。
- **状态**：通用凭证中已明确识别的待支付、失败、关闭、撤销及退款状态会提示核对；明确带正号的无标签收入金额会提示收入。

## 查重规则

按证据建立索引，只比较可能相关的记录，结果在首页标记重复，不自动删除或合并原图。

- 相同照片 SHA-256 是独立依据。
- 微信支付、微信转账、支付宝单号分别比较，同一交易的截图与电子凭证可以通过完整平台单号关联。
- 两个完整平台单号不同时，不使用相同商户订单或金额时间等弱证据判重。
- 商户单号需结合收款方；金额时间规则需同时匹配收付款方。
- 通用单号可能只是内部序号，需结合机构、商户、金额、有效且精确到秒的交易时间。只有日期的通用凭证不靠单号自动判重。
- 通用凭证的自动判重采取保守策略；缺失充分证据可能漏报，而不会为提高命中率放宽到“商户+金额”相同即判重。

## 存储、恢复和错误处理

- 同一浏览器、同一网址才能访问原有凭证。完整网站 ZIP 不是用户凭证数据备份；凭证数据请使用网站菜单里的 ZIP 备份功能。
- 保存记录与图片使用 IndexedDB 事务。容量不足时提示备份、释放空间并重试，不虚报保存成功。
- 恢复前校验 ZIP 条目、总解压大小、记录格式、重复 ID、路径、CRC、照片 SHA-256。验证全部通过后才在一个事务内替换，写入异常回滚。
- 为保留既定数据保护行为，删除列表记录不清理底层历史照片；长期使用可能占用额外空间，不作自动破坏性清理。
- Worker 崩溃、初始化超时或消息发送失败后释放失效引擎，后续可以重新初始化。
- Service Worker 使用内容版本切换静态缓存，模型按大小与 SHA-256 校验，不把网页更新当作清空凭证的理由。

## 界面参数与维护约束

- 适配桌面、600px 以下手机、360px 以下窄屏；横向边距同时考虑安全区域。
- 主要操作点击区域至少 44px；输入框 16px 字体，减少 iPhone 输入自动放大。
- 总金额根据容器宽度与字符数量调整字号，防止小数末位单独换行。
- 首页商品标题最多两行；长文件名/单号可换行，识别弹窗固定两行文件名空间以减少跳动。
- 识别弹窗只保留一个标题、进度、数量、文件名与本地提示，不恢复重复副标题或停止按钮。
- 普通交互过渡约 140–220ms，减少动态效果偏好会关闭动画；深色模式有独立颜色变量。
- 保留用户指定的简洁操作和按钮焦点外观，不引入额外审核流程或大型 UI 框架。

## 修改后的验证

安装依赖后先 `pnpm build`，再 `pnpm test`。预览服务测试需要已生成的 `dist/`。已知支付截图规则修改后，还应在本机使用实际 OCR 样本比对金额、时间、收款方、单号和商品描述。真实照片不得提交仓库或放入公开交付包。

算法是本地 OCR + 确定性规则与自动补扫，不是在线训练系统，无法保证模糊、无标签或互相矛盾的任意版式全部正确。桌面测试时间不代表手机硬件耗时。
